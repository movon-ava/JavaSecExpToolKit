# 漏洞分析模块设计评估与演进建议

更新时间：2026-09-23（基于仓库现有文档与进度记录）  
适用范围：JavaSecExpToolKit 漏洞分析模块  
目的：评估“复用 jar-analyzer 的分析结果，再做项目内二次研判并跳转利用模块”的思路，给出可持续演进路径。

## 1. 结论

你的方向是合理的，但模块定位不应是“再实现一个 jar-analyzer”，而应是：

> **外部分析器负责尽可能完整地提取事实；本项目负责把事实转成有证据、有边界、可验证的安全假设，并把分析上下文交给后续验证或利用工作流。**

按仓库 README、`docs/DESIGN-analyze.md`、`PROGRESS.md` 和 `AI_REPORT.md`，这个方向目前已经有实质实现：

- 本地依赖分析读取 Maven 坐标，按版本规则输出组件漏洞结论；
- 调用链分析可运行用户提供的 `jar-analyzer-engine`，查询其 SQLite 数据库；
- 对入口点、Sink、字符串、组件和总体数据进行查询；
- 由本项目维护的签名库对事实进行二次匹配，归纳可能的漏洞类型及常见绕过手法；
- 需要核实时可定点反编译，并提供跳转到已有功能页的建议；
- 依赖口径与代码口径已经拆为独立页面。

因此建议进入**可靠性与分析工作流增强阶段**，而不是重写基础扫描器。尤其要避免把“组件存在”“危险调用存在”“存在可控输入”“漏洞可利用”合并成一个结论。

## 2. 建议的职责边界

| 层次 | 回答的问题 | 数据/能力 | 结论措辞 |
| --- | --- | --- | --- |
| 采集事实 | 包里有什么、代码里有哪些结构 | jar-analyzer 输出、依赖元数据、调用图、常量、入口点、Sink | “观察到 / 引擎报告” |
| 证据关联 | 危险行为是否与入口存在静态路径或结构关联 | 入口点、调用边、Sink、类与方法、污点/参数线索（若上游提供） | “存在候选路径 / 未证明可控” |
| 风险研判 | 这些事实更像哪类漏洞，成立需要什么条件 | 本项目版本化的规则与漏洞知识库 | “可能 / 需要确认”，列出命中证据及缺失条件 |
| 验证建议 | 如何在授权范围内确认或排除假设 | 已有探测、Shiro、Payload、代理等模块 | 提供安全的下一步操作，不自动执行 |
| 利用工作流 | 将使用者确认过的分析上下文传入对应功能 | 模块间显式上下文对象 | 用户确认后跳转和预填，不静默发包 |

依赖中出现某个 gadget 库，只能说明 classpath 中存在相关组件；Sink 命中只说明代码中存在危险调用；入口点被枚举出来，不证明入口到 Sink 的路径可达；即便存在路径，也不自动证明关键参数受外部控制或目标配置满足触发条件。这些状态应分别呈现。

## 3. 推荐工作流

```text
选择 jar / 依赖目录
        |
        +--> 本地快速分析：组件坐标、版本、规则命中、gadget 依赖齐备情况
        |
        +--> （用户显式触发）外部引擎建库
                    |
                    +--> 查看入口点、Sink、组件与字符串等原始事实
                    |
                    +--> 运行本项目规则：漏洞假设 + 命中证据 + 未满足条件
                    |
                    +--> 针对选中的类/方法反编译、人工复核
                    |
                    +--> 用户选择下一步：探测 / Shiro / Payload / 代理 / 仅导出报告
```

外部引擎昂贵且可能不可用，故应保留当前“快速分析先行、深度分析按需”的分层。每个耗时动作需要明确输入、输出目录、耗时、取消/超时状态和失败原因；不能让用户把“建库失败”误解为“没有漏洞”。

## 4. 外部工具集成原则

### 4.1 把 jar-analyzer 当作可替换的分析后端

JavaSecExpToolKit 不应依赖上游数据库的内部细节作为长期稳定 API。当前设计通过 `EngineRunner`、`ReportReader` 和单一命令契约封装外部进程，这是正确的隔离方向。建议继续把集成收敛为适配器边界：

- 记录引擎版本、命令行参数、输入文件摘要、数据库生成时间和引擎退出码；
- 明确检查数据库是否存在、大小是否合理、必要表/列是否存在；数据库缺表或 schema 变化应显示“不兼容/部分可用”，不能显示“零命中”；
- 将引擎输出统一规范化为本项目内部的数据模型，UI 不直接依赖 SQLite 表名；
- 将超时、用户取消、引擎崩溃、数据库损坏、无结果区分为不同状态；
- 只读查询与引擎写库分离。已有 `mode=ro` 查询约束应保留；
- 对输入 jar 和引擎路径做可读性、目录权限和大小检查，避免把路径错误延迟到漫长任务结束后才暴露。

README 对引擎的许可和实现依据有记录，但集成前仍应对**实际分发的 engine 版本、许可证文本、数据库 schema 及升级策略**单独核对。不要复制上游 GPLv3 GUI 侧的签名、规则数据或资源文件；可以实现独立规则，但规则来源、许可证与更新时间需留档。

### 4.2 兼容性策略

建议在内部报告元数据中保存：

- 外部引擎名称与版本；
- 内部 schema 版本；
- 目标文件 SHA-256（可选配置脱敏或不持久化）；
- 分析开始/结束时间与任务状态；
- 各数据源是否可用、被跳过或解析失败。

当引擎升级导致数据库结构变化时，适配器可以按 schema 能力降级展示，而不是静默返回空结果。真实引擎端到端测试应作为发布门槛之一；目前仓库记录明确说明尚未持有 engine，现阶段验证止于命令拼装、失败路径和模拟数据库查询，这是重要的已知风险。

## 5. 内部报告模型建议

现有 `Finding`、`AnalyzeReport` 和签名库是不错的起点。后续可逐步把报告条目规范成以下结构，避免报告文本承担唯一数据契约：

```text
Finding
  id                 稳定标识
  category           vulnerability / gadget / configuration / secret
  title              人类可读标题
  status             observed / suspected / confirmed / not-reproduced / unknown
  confidence         high / medium / low，并说明评分依据
  evidence[]         来源、类/方法/行号或数据库记录、命中规则版本
  prerequisites[]    成立前提，例如外部可控、特定配置、受影响版本
  missingEvidence[]  当前缺少的证明
  affectedComponent  groupId / artifactId / version / 来源可信度
  suggestedAction    建议动作，不等同自动执行
  references[]       公告、CVE、项目文档等外部来源
```

建议区分 `observed`、`suspected`、`confirmed`、`not-reproduced` 和 `unknown`。静态特征命中不应标为 confirmed；扫描失败也不应标为 clean。严重度、置信度、可达性是不同维度，不宜压成一个分数。

对于每一项结论，报告至少应展示：**命中什么、从哪里命中、为什么支持该假设、仍缺什么证据、哪些条件会使它不成立、下一步如何验证**。可把“绕过手法”作为知识提示，但必须标注适用版本、前置条件和来源；不要把某类漏洞的所有绕过技巧无差别地贴到每个命中目标上。

## 6. 如何分析过滤与绕过

“有哪些过滤、怎么绕过”应成为**证据驱动的分析问题**，不宜只做静态技巧清单。建议把每个绕过条目拆成：

1. **过滤点**：过滤器/校验器类、方法、规则或配置，及其调用位置；
2. **输入路径**：入口参数到过滤点、再到危险 Sink 的候选关联；
3. **约束语义**：允许字符、拒绝字符、类型白名单、编码/规范化顺序、大小写处理、递归深度、签名/完整性校验等；
4. **绕过假设**：特定编码、类型包装、双重解析、别名或解析器差异为何可能改变判定；
5. **反证条件**：规范化发生在校验之前、参数不可控、后端再次校验、版本已修复等；
6. **验证方式**：优先使用无害输入和离线/本地验证；需要发包或生成可执行载荷时要求用户明确确认授权范围。

若 jar-analyzer 只产出调用图、常量和类/方法信息，并不产出污点分析或过滤器语义，那么本模块不能声称已证明“可绕过”。此时应写成“发现候选过滤逻辑；需要人工确认输入是否经过该逻辑及后续使用方式”。这能显著降低把 gadget 存在或字符串命中误说成可利用漏洞的风险。

## 7. 与利用模块的衔接

跳转应传递**可审阅的分析上下文**，不应只切换页面，也不应自动向目标发送请求。建议定义轻量的 `AnalysisContext`（具体落地时按现有模块边界拆 change）：

- 目标 jar / 组件坐标与版本；
- 当前 finding 标识和证据摘要；
- 入口类、方法、候选 Sink；
- 已知目标地址（只有使用者显式提供时）；
- 推荐功能页与预填字段；
- 上下文来源和生成时间。

跳转到探测、Shiro、Payload 或代理页时：

- 页面应显示“由哪条分析结论带入”，并保留返回分析结果的路径；
- 只预填有明确映射的字段，不能把类名、常量或推测自动塞进命令/回连地址等高风险参数；
- 任何网络请求、载荷生成、服务器启动或文件写入都需用户主动操作；
- 若无法形成可信映射，显示建议而不伪造预填值。

仓库已有建议按钮跳转，这是良好基础。下一步应让按钮带上 finding id 和证据，而非让目标页只收到一个页面路由。

## 8. 当前设计优点

基于仓库文档，以下决策值得保留：

- 复用外部引擎，不复制重做调用图构建；外部工具缺失时本地依赖分析仍可用；
- 引擎数据库查询只读，外部进程有工作目录和超时边界；
- `analyzer` 为叶子层、`analyze` 只依赖 `analyzer`，UI 与分析内核分开；
- 依赖来源随结论保留，低可信来源明确降级；版本不可比时不匹配，避免静默误报；
- 区分“依赖存在”与“链可达”，报告明确提示边界；
- 规则由项目自有数据维护，关注许可边界；坏规则行可见报错，不静默跳过；
- 漏洞特征与 Sink 清单通过测试做一致性守卫；严重度过滤和特征覆盖有单测；
- 配置页保存引擎路径、工作目录、超时等长期配置；
- 两类分析拆页，避免秒级依赖结论与分钟级建库混在同一操作里。

## 9. 当前不足与优先级

### P0：真实外部引擎端到端验证

这是当前最明确的验证缺口。使用固定版本的 engine 和可公开/自建的小型测试 jar，验证完整链路：启动参数、工作目录、数据库生成、表结构识别、查询、异常退出与清理。测试数据应只在本地/测试环境运行，不触碰未经授权目标。没有真实引擎可用时，界面必须清楚标注功能未配置，而不能把模拟库测试当成端到端通过。

### P1：结果状态与证据来源

引入统一状态与数据源状态，至少区分：未运行、运行中、成功、部分成功、失败、超时、取消、结果不兼容。每个 Finding 保留命中数据、规则 id/版本、引擎版本和置信度依据。避免“0 命中”掩盖“查询没执行成功”。

### P1：规则知识库治理

漏洞规则、Sink 清单、绕过提示需带稳定 id、适用组件/版本、成立条件、反例、参考来源、维护日期和规则版本。新增规则时增加正例、负例与边界测试。绕过提示应按命中事实筛选，不仅按漏洞大类整体贴出。

### P1：证据关联与可达性表达

若外部引擎能提供调用路径，报告应展示入口到 Sink 的路径及路径长度/断点；若不能，则明确说明目前只有独立命中，不能推断二者连通。后续若扩展污点分析，应先以单一漏洞类型做小范围验证，并把“源/传播/净化/Sink”证据模型定义清楚。

### P2：分析任务和结果可复现

保存分析任务元数据、规则版本、工具版本与目标摘要；允许对同一输入重跑并比较结果变化。持久化之前先决定敏感路径、常量、令牌等数据如何脱敏、保留多久和如何删除。避免将完整 payload、凭据或敏感常量写入普通日志。

### P2：交互与报告导出

支持按严重度、状态、组件、证据来源筛选；结论列表与证据详情分区；导出可机器读取的 JSON，同时保留面向人工的报告。导出需注明分析时间、工具/规则版本、数据源和局限。避免仅提供一个大文本框作为唯一结果形态。

## 10. 推荐实施顺序

1. **先验证接口事实**：确认用户所说的 `jar-analyzer` 具体版本、许可证、实际 engine 产物、输入参数与数据库 schema；补真实端到端测试夹具。
2. **建立报告契约**：明确事实、推断、验证状态的区别，补失败/部分结果状态与证据来源。
3. **补足规则治理**：先把现有签名和绕过提示补充来源、适用条件、反例及版本范围；加强负向测试。
4. **增强证据关联**：在外部数据实际支持的范围内呈现入口/Sink 路径；不支持时明确标为未知，不自行推断可达。
5. **改进分析到工作台的交接**：点击建议按钮传递 Finding 上下文，先预填、展示、由用户确认，不自动执行。
6. **再考虑新增分析能力**：例如自有的轻量过滤器识别、参数可控性分析或更广的漏洞类型覆盖。每项先做准确率可测的小范围实验，不以规则数量作为完成指标。

跨多个代码写入域的实施应按项目 OpenSpec 约束拆分；本文件是设计评估，不代表已经建立对应 change 或批准实现。

## 11. 安全与合规边界

- 工具仅面向已获授权的样本与目标；静态分析结果不等价于漏洞确认。
- 外部引擎仅对本地样本运行；不得未经确认自动上传 jar、数据库或报告。
- 报告中的绕过知识用于授权验证和修复研判；网络验证、载荷生成、投递与服务器启停都由用户显式触发。
- 规则与知识数据保留来源、许可证和适用版本，避免复制上游受限数据文件。
- 日志记录任务状态与摘要即可，避免写入密钥、令牌、完整请求/响应或可执行载荷。

## 12. 总结

项目当前的架构方向已经成立：使用 jar-analyzer 提供代码事实，用本项目自己的规则和功能模块把事实转成可行动的研判。这正是成熟外部工具能带来的杠杆：省下重做底层扫描器的成本，把工程投入放在**证据质量、误报控制、规则来源、可达性表达和安全的工作流衔接**上。

最值得优先推进的不是“再加更多绕过条目”，而是让每条结论都能回答：**依据是什么、证据从哪里来、还缺什么条件、什么情况会推翻它、下一步可以安全地做什么**。做到这点，漏洞分析模块才会成为利用模块之前可信的研判层，而不是仅仅把扫描输出换一种格式展示。
