# process/multi-agent-concurrency Specification

## Purpose

规定多 Agent 并行开发时的隔离、协作与运行健康边界，使「互不干扰」与「任务是否还在推进」
都成为可核对的客观事实，而不是依赖执行者自觉。

## MODIFIED Requirements

### Requirement: 角色会话必须有超时上限

系统 SHALL 为每个角色会话设定超时上限，使运行过久的会话能被终止并保留判断依据。

超时判定 SHALL 区分「正常的长等待」与「实际卡死」两类停滞，不得仅凭一段时间内
日志无新增就判定为卡死。

超时时系统必须终止该会话及其子进程，并保留现场与日志；不得在未完成的情况下
将产出视为可用结果。

#### Scenario: 超时会话被终止
- **WHEN** 角色会话运行时间达到超时上限
- **THEN** 该会话及其子进程被终止，且打印出超时提示与日志尾部

#### Scenario: 超时不会污染仓库
- **WHEN** 会话因超时被终止
- **THEN** 未完成的改动不会被提交，现场保留在该会话的独立工作区中

#### Scenario: 长等待不被误判为卡死
- **WHEN** 日志因等待一条耗时命令而长时间无新增，且日志内容显示存在明确的等待对象
- **THEN** 判定结论为「正常等待」，会话不被终止

#### Scenario: 真卡死会被识别
- **WHEN** 日志内容显示反复重试同一条命令或重复同一错误，且无明确等待对象
- **THEN** 判定结论为「卡死」，会话被终止并保留日志

## ADDED Requirements

### Requirement: 停滞判定必须独立于执行者

系统 SHALL 由一个独立的只读看护 agent 依据日志内容判定会话处于推进、长等待
还是卡死，且该 agent 不得修改仓库或终止进程。

终止动作只由持有进程句柄的启动脚本执行，不由判定方执行。

#### Scenario: 看护 agent 只读
- **WHEN** 看护 agent 被唤起判定某会话状态
- **THEN** 它以只读沙箱运行，不能修改任何文件

#### Scenario: 判定结论可追溯到日志
- **WHEN** 看护 agent 给出判定结论
- **THEN** 结论包含状态、理由，以及与理由对应的日志证据

#### Scenario: 判定不可用时保守处理
- **WHEN** 看护 agent 未能给出可解析的判定结论
- **THEN** 会话不被立即终止，而是按原超时上限继续等待
