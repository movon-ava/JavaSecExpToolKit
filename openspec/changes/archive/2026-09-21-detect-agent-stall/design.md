# Design

## Context

`tools/agent.ps1` 目前用 `Start-Process` + `Wait-Process -Timeout` 等待会话结束。
这个机制只能回答「进程有没有退出」。本仓库已实际发生过两种相反的误判风险：

- 上一轮监督审计跑了约 15 分钟无结论，属于真实的「长时间无产出」；
- 而实测执行 `ping -n 400` 时，会话会静默数分钟，日志在这段时间**完全无新增**，
  但这属于正常等待。

两者在「日志静默时长」这一维度上不可区分，因此单靠时间阈值无法判定。

## Goals / Non-Goals

**Goals:**

- 用日志内容区分「推进中」「正常长等待」「卡死」三态，减少误判。
- 判定由独立只读 agent 完成，与执行者解耦，符合本仓库既有的监督式设计。
- 判定失败时保持保守（不终止），避免把可用会话杀掉。
- 复用既有 codex CLI，不引入任何第三方依赖。

**Non-Goals:**

- 不做自动修复（不自动重试、不改写任务）。
- 不让 LLM 直接杀进程；终止只由持有进程句柄的启动脚本执行。
- 不改变总超时上限作为兜底的地位。

## Decisions

### 决策 1：三态结论而非二值

判定输出 `PROGRESSING` / `WAITING` / `STUCK` 三态。二值（活着/卡死）无法表达
「在等一条已知的长命令」这一最常见情形，必然导致误杀。

### 决策 2：判定依据是日志「末尾窗口」而不是计数器

看护 agent 读日志尾部若干行（默认 120 行），判断是否存在：
明确的等待对象（正在运行的命令、显式等待语句）、推进痕迹（新的工具调用、
新的输出块）、或重复模式（同一命令/错误反复出现）。
不采用「行数增量」作为唯一依据，因为长命令执行期间行数确实不增。

### 决策 3：节奏与阈值

启动脚本每 `PollSeconds`（默认 60 秒）检查一次日志大小与修改时间；
连续 `StallRounds`（默认 2 轮）无变化才唤起看护 agent，
避免频繁调用造成额外开销。总超时上限仍独立生效。

### 决策 4：判定不可解析时保守继续

看护 agent 的输出需要包含一行机器可读结论（`VERDICT: <状态>`）。
解析不到该行时按「无法判定」处理：继续等待，不终止。

### 决策 5：抽出共用库

启动与看护都要「定位 codex 可执行文件」。把它抽到 `tools/lib/CodexCli.ps1`，
避免两处各自维护一份路径探测逻辑。

## Risks / Trade-offs

- **误判仍有残留**：LLM 判断不是形式化证明。因此设计上让「终止」成为需要
  明确 `STUCK` 结论才发生的动作，且总超时兜底始终存在。
- **看护本身也有成本**：每轮停滞判定会消耗一次模型调用。用 `StallRounds`
  控制触发频率，默认两轮静默才判定一次。
- **看护 agent 只能看到日志**：若任务卡在日志之外（例如工具无输出），
  判定可能偏向 `WAITING`。这是刻意选择的保守方向：宁可多等，不可误杀。
