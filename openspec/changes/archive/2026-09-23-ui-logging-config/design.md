# Design: 日志配置进入配置页

## Root Cause

问题不在「配置页少了一项」，而在**启动时机**：日志必须在最需要它的那一段之前就绪。

当前的启动顺序是「组合根建控件 → 读配置 → 建控制器 → 预热（约 1 至 2 秒，
java-chains 元数据最重）→ 显示窗口」。如果日志初始化跟在「读配置」之后，
那么配置读取本身、控件构建、以及整个预热过程都处于无日志状态——
而这几步恰恰是最容易在别人机器上出问题的地方。

因此本设计把两件事分开：
配置的**读取**仍然由配置页负责（它是配置的唯一真相），
而日志的**初始化**必须在读配置之前用默认值先做一次，读到配置后再按配置重做一次。

## 设计

### 两次初始化

| 时机 | 目的 | 取值来源 |
| --- | --- | --- |
| 进程启动、读配置之前 | 保证最早的失败也有记录 | 内建默认值（启用、常规级别、用户目录） |
| 读取配置之后 | 让使用者的设置生效 | 配置页保存值 |

`configure` 幂等且可重复调用：第二次调用会按新设置重开当天文件（追加，不覆盖）。
这样既不会丢失启动瞬间的记录，也不会让使用者的设置不生效。

### 目录解析的优先级

沿用内核既有的三级解析（环境变量 > 配置项 > 用户目录默认值），
配置页只负责「写配置项」与「显示最终生效值」。显示用的是解析后的结果而不是原始输入，
否则使用者填了相对路径、或环境变量覆盖了配置，界面上会显示与实际不一致的路径。

### 默认值取舍

| 配置项 | 默认 | 理由 |
| --- | --- | --- |
| 是否启用 | 启用 | 排错能力不该需要使用者先手动打开；关闭随时可改 |
| 级别 | 常规 | 记录生命周期与失败路径，不记调试细节，日志量可控 |
| 目录 | 用户目录下的默认位置 | 安装目录可能只读；与配置文件同级便于一起备份 |
| 保留天数 | 7 天 | 足够回溯一轮测试；乘以单日量仍在小体量 |
| 控制台回显 | 关闭 | 从图形界面启动时没有控制台，打开只是噪音 |

### 级别候选取值

配置里保存英文标识、界面显示中文名，两者按下标对应（仓库既有约定）。
这样级别取值可以稳定地出现在配置文件里被脚本读取，而界面上不必出现英文。

## 边界

- 只新增一个配置分组与对应键，既有键与分组不动。
- 不修改内核的行为与签名；内核改动见 change `logging-core`。
- 配置文件格式不变（仍是 `Properties`，UTF-8），Python 侧读取不受影响。

## 本设计不改变哪些既有行为

- 既有全部配置项的键名、默认值与下发时机：不变。
- 启动预热的步骤、顺序与「失败不阻断启动」的行为：不变。
- 窗口尺寸、导航结构与既有页面：不变。
