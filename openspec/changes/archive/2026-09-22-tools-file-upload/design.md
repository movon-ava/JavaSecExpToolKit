# Design: 小工具 - 文件上传

## 一、Root Cause：为什么不能复用既有的 capture 模式

**现象**：抓包页与 Shiro 页都能发请求，但没有任何一项能把本地文件发出去。

**成因**：`capture` 模式的请求体是 `str`（`_request_raw` 内部固定
`body.encode("utf-8")`），并且请求体由界面直接给出。文件上传有两处**结构性**不兼容：

1. **字节 vs 文本**：文件可能是任意二进制，先按 UTF-8 编解码一次就会破坏内容
   （非法字节序列被替换成 `\ufffd`），上传上去的文件与本地文件不再一致；
2. **分段 vs 单块**：`multipart/form-data` 需要按 boundary 拼出多段（普通字段段 + 文件段 +
   结束分隔符），并且 `Content-Type` 必须带上同一个 boundary，二者不一致时目标解析不到文件。

因此不是「参数没传对」，而是既有请求体通道的**类型**不支持，必须新增一条字节通道。

**改法**：

- Python 侧把 `_request_raw` 拆成 `_request_raw`（文本，行为不变）+ `_request_bytes`
  （接受 `Optional[bytes]`），两者共用同一套请求头净化与 `_NoRedirect`；
- 新增 `_upload(ctx)`：读文件 → 用 `uuid4().hex` 生成 boundary → 按字节拼 multipart →
  `_request_bytes` 发送 → 记录状态码 / 耗时 / 响应头 / 响应体 / Set-Cookie；
- 内容即结果，因此 `upload` 与 `capture` / `convert` 一样**强制详细报告**。

## 二、边界：本设计不改变哪些既有行为

- `capture` / `convert` 的请求体仍是文本路径，`_request_raw` 的对外签名与返回结构不变；
- `detect` / `version` / `expect` / `dns` / `ceye` 五个模式完全不动；
- 代理页与抓包页不新增任何入口，上传结果也不进「一键发送」链路；
- 配置页既有分组与配置键不动，只在末尾新增一个分组。

## 三、失败路径的可观测结论（不静默）

上传的失败必须给出人能直接照做的结论，而不是空结果或 Python 异常：

| 情况 | 结论 |
| --- | --- |
| 目标 URL 为空 | `上传目标 URL 不能为空` |
| 未选择文件 | `未选择文件：请先选择一个本地文件再执行上传。` |
| 路径不存在 / 不是普通文件 | `未发送请求：<路径>：不是可读的普通文件` |
| 文件超过单文件上限 | `未发送请求：<路径>：N 字节超过单文件上限 M 字节` |
| 附加字段不是合法 JSON | `附加表单字段不是合法 JSON：<原因>` |
| 连接失败 | `上传失败：<原因>` + 「确认目标可达、端口开放」提示 |
| 3xx | 保留原始响应，提示「不跟随跳转」并给出 Location |
| 401 / 403 | 提示「把会话 Cookie 填进请求头后重试」 |
| 5xx | 提示「确认上传字段名与目标接口一致」 |
| 404 | 提示「确认上传接口路径正确」 |

## 四、单文件上限与并发

单文件上限取 8 MB：上传功能用于验证接口可达性与响应格式，8 MB 足够覆盖常见的样本文件，
又不会把桌面端内存与目标磁盘打满。超限时**跳过该文件并给出可读结论**，不静默截断——
截断后的文件与本地文件不一致，会让使用者拿着错误的样本继续排查。

## 五、界面结构

沿用仓库既有的「视图 `*Page` + 行为 `*Controller`」两段式：

- 视图：`ToolsUploadPage`（`Widgets` + `defaults()` + `build()`），`JFileChooser` 实例也在
  `defaults()` 里建好，行为类不 new 任何控件（与依赖边界规格一致）；
- 行为：`ToolsUploadController` 负责选文件、拼参数、后台线程跑引擎、回填结果、复制结果；
- 配置：默认 URL / 字段名 / 请求头在启动与保存后各下发一次，与代理页、抓包页同源。
