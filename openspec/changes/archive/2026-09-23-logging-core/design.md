# Design: 日志内核

## Root Cause

排错困难的成因不是「没写日志」这么笼统，而是三个具体缺口：

**缺口 1：异常被静默吞掉。** 源码里大量 `catch (XxxException ignored)`，注释写着
「不影响主流程」——判断本身没错（单条连接失败确实不该拖垮代理），但它们把
「发生了什么」也一起丢掉了。结果是功能「看起来没反应」，而不是「报错」。

**缺口 2：后台线程的异常无处可去。** 代理连接线程、隧道泵线程、引擎输出读取线程
抛出的异常只会打到标准错误；从图形界面启动时标准错误没有接收方，等于消失。

**缺口 3：没有时间基准。** 即使事后拿到一些线索，也无法回答「这个问题是今天出现的，
还是一周前就有」——没有按时间落盘的东西可查。

本设计要解决的是这三条，而不是「加一个通用日志框架」。

## 设计

### 为什么内核放在共享内核层

日志必须能被**任意**模块调用。本仓库的依赖方向被约束为单向（见 `codebase/dependency-boundary`），
功能模块之间不允许互相依赖，因此日志只能沉到被所有层依赖的共享内核里。
这一层的代价是**不许有任何出边**：内核不能反过来引用界面或任何功能包，
只能依赖 JDK 标准库。级别过滤、目录解析、清理，全部自包含。

### 两个类，一条职责分界

| 类 | 职责 | 判定方式 |
| --- | --- | --- |
| 文件名与保留策略 | 名字怎么拼、哪个名字代表哪一天、哪些该删 | 纯计算，可脱离文件系统断言 |
| 记录通道 | 级别过滤、时间戳、异常栈、落盘、跨天切换 | 真实写文件 |

拆开的理由是「保留天数是否算对」属于最容易写错、又最不该靠造文件去猜的一类逻辑。
分界一旦划清，规则层可以被逐条断言（含跨月、跨年、天数边界），
而写入层只需验证「真的写进了当天文件、跨天真的换文件」。

### 关键取舍

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 写入失败怎么办 | 静默丢弃这一条 | 日志是旁路。让它影响主流程，比没有日志更糟 |
| 并发写入 | 单一锁内串行写 | 日志量远低于吞吐瓶颈；无锁队列会引入丢行与顺序错乱 |
| 保留语义 | 「最近 N 天，含今天」 | 与使用者直觉一致；写成「N 天前开始保留」会多留一天 |
| 保留天数越界 | 归一到 1 | 填 0 或负数多半是手滑；若按字面执行会把正在写的文件一并删掉 |
| 清理频率 | 启动一次 + 跨天一次 | 每次都扫目录是浪费；只在启动清理又会漏掉长期运行的会话 |
| 日期来源 | 可替换 | 跨天切换无法靠等待验证，必须能把日期注入进来 |

### 清理的安全边界

`定期清理` 的破坏性来自「删错东西」，因此设三道闸：

1. 只有严格匹配 `app-yyyy-MM-dd.log` 的名字才进入候选，目录里其它文件一律不碰；
2. 候选必须是常规文件，且其父目录恰好是日志目录自身（越界即跳过）；
3. 单个文件删除失败（被占用）只跳过，不中断清理、不影响写入。

日志目录默认落在用户目录下、与配置文件同级，避免写进安装目录（可能只读）。

### 目录解析为什么沿用「环境变量优先」

探测引擎解析 Python 解释器时已是这条口径。沿用它的好处是自检与便携场景不必改配置：
把目录指向临时目录即可把日志引开，而使用者看到的行为与配置页一致。

## 边界

本设计不改变任何既有行为：不接管标准输出、不改任何既有类的对外方法签名、
不修改既有配置项的语义。新增的只是一个可被调用的记录通道。

## 本设计不改变哪些既有行为

- 全部功能模块的对外行为与既有配置项：不变。
- 构建依赖清单：不变（未新增依赖）。
- 既有自检与单元测试：断言只增不减。
