# Design

## Context

`Payload 生成` 页在 change `java-chains-workbench` 中落地时的交互是
「四个控件串成一条流水线」：`载体分组` → `载荷载体` → `追加节点` → `追加节点` 按钮。
本次把这条流水线替换为网页版 java-chains `Generate` 页的**列式选择器**。

改动前的实测事实（决定了改法，不是推测）：

| 实测项 | 数值 / 结论 | 来源 |
| --- | --- | --- |
| 运行时载体数 | 28 | `PayloadCheck`，`PayloadEngine.payloadIds()` |
| 运行时节点数 | 429 | `MetadataRegistry.getNodeMetaMap()`，现场实测 |
| 单个载体的首节点候选 | 上百项量级（`javanativepayload` 实测过百） | `PayloadEngine.firstNodes` |
| 28 个载体全量首节点校验耗时 | 71 ms（约 0.3 ms/候选） | `docs/DESIGN-payload.md` 九节 |
| 节点显示名的可得性 | 429 个节点里 426 个有非空显示名 | `MetadataRegistry.getNodeMetaMap()`，现场实测 |
| 载体显示名的语言 | 中文（例如 `Java原生序列化Payload载体`） | 同上 |

约束：Java 编译目标 release 8（禁用 `var` / `List.of` / `switch` 表达式）、Swing 界面、
唯一第三方依赖 java-chains 2.0.0-beta4、界面视图与行为分离（主 spec `codebase/dependency-boundary`）。

## Root Cause

**成因是「候选集合只有一种呈现方式」，不是缺功能。**

1. **状态模型按「尾部」组织。** 链状态 `ChainEditor` 只暴露 `head` / `tail` /
   `candidates()`（取尾部候选），界面因此只能回答「当前链末尾还能接什么」。
   「第二层还能换成什么」这个问题在状态模型里没有入口，于是界面只能提供
   `删除末节点`，让使用者用「退到第二层」的方式间接实现「改第二层」。
2. **候选集合被绑死在下拉框上。** 候选一律渲染进一个 `JComboBox`，
   而 Swing 下拉框没有层级概念：上百个候选只能压成一维列表逐个翻找，
   也看不出「这些候选属于第几层」。分组下拉框是为了让「28 个载体」在一维列表里可用
   而补的辅助维度——它不是链的语义，只是列表的替代索引。
3. **两处合起来导致：链越长，改中间层越贵。** 追加 N 次要点 2N 次控件，
   改第 K 层要先退 N-K 次。这是结构决定的下限，靠调整文案或加按钮无法解决。

因此改法不是「给下拉框加个搜索框」，而是把**层级**引入状态模型与视图：
状态变为「按列保存候选集合 + 当前选中的列索引」，视图按列渲染，点击某一列的候选
即以该列为界重开链。这样「改中间层」从「退 N-K 次」变成一次点击。

## Goals / Non-Goals

**Goals:**

- 链的构建与修改都只需一次点击：点候选 = 追加并展开下一列；点前面某列的候选 = 从该列重开链。
- 候选始终只来自引擎（`PayloadEngine.firstNodes` / `nextNodes`），界面不内置任何节点关系表。
- 候选上百项的列必须能被快速收敛（关键字过滤），过滤只影响展示，不影响链状态。
- 第一列直接是载体，`载体分组` 与 `载荷载体` 两个下拉框连同它们占据的两行一起消失。
- 保留既有的「删除末节点」「清空链」与只读链文本，链的手工回退路径不断。
- 载荷引擎零行为漂移：只新增只读的显示名查询。

**Non-Goals:**

- 不做网页版 Generate 的周边能力：暴力矩阵、步进调试、分享链、常用统计、保存预设、
  Tag 筛选与并集/交集、输出解析。
- 不改预设链页与恶意服务器页；后者的 `载体分组` + `载荷载体` 下拉框保持原样
  （那是发布流程，不是本页的选链体验）。
- 不改载体分组表 `PayloadCatalog`：它继续为恶意服务器页提供分组视图。
- 不做分支型链（一个节点接多个后继后再汇合）：本页仍是线性链。
- 不引入新依赖，不改共享内核，不新增可持久化配置项。

## Decisions

1. **列式选择器单独成类（`ui/PayloadChainSelector.java`），不放回 `PayloadPage`。**
   理由：主 spec 要求单个界面文件不超过 600 行，`PayloadPage` 目前约 290 行，
   列式选择器的列容器、列渲染、过滤框、横向滚动与点击路由合计约 200 行，
   合进去会逼近上限；且选择器不持有链状态（状态仍在 `ChainEditor`），
   把它做成「视图组件」与既有 `UiKit` 的分工一致。
   替代方案：塞进 `PayloadPage` —— 单文件变大且与「视图只搭结构」的分工混淆。

2. **层级状态放在控制器，不放在选择器。**
   选择器只暴露「按列渲染什么、点某列某项时回调谁」；「当前链有几列、每列候选是什么」
   由控制器按 `ChainEditor` 现算。理由：链的权威是 `ChainEditor`（与恶意服务器页共用），
   若选择器也存一份候选，两处会漂移。
   替代方案：把候选缓存进选择器 —— 换载体时会出现「旧候选还在」。

3. **点击某一列的候选即截断该列之后的所有节点，而不是「只换这一项」。**
   理由：后续列的候选本来就依赖前一项，保留后续列会得到一条引擎不认可的链
   （`ChainEditor.candidates()` 按尾部候选计算，截断后必须重算）。
   网页版 Generate 的行为也是「点第 N 列的新候选即从第 N 列往后重建」。

4. **过滤框只影响该列渲染出的项，不影响状态。**
   理由：若过滤直接改候选集合，使用者清空关键字后必然要重算一次，
   且「当前选中项被过滤掉」会让链文本与列表看起来不一致。
   因此过滤是渲染期的 `contains` 判断，选中项始终保留在列表首位（避免看起来像被清掉）。

5. **载体列不放在第一列的过滤之后，而是直接使用 `PayloadEngine.payloadIds()` 的字母序。**
   理由：28 个载体一屏可容纳，字母序与 `PayloadCheck` 的目录断言同一来源，
   不再需要本地分组表；分组表仍供恶意服务器页使用。

6. **显示名走新增的只读查询，取不到时回退成标识。**
   理由：实测 429 个节点中 3 个没有显示名（例如 `clojure`），
   若直接展示空字符串，列里会出现看不见文字的项；回退成标识可读且不丢信息。

## 与既有模块的边界

- `src/payload/PayloadEngine.java`：只新增 `nodeLabel(String)` 一个只读方法；
  既有 10 个公开方法的签名与语义零改动（`PayloadCheck` 61 条断言一条不改）。
- `src/ui/ChainEditor.java`：**零改动**。列式交互所需的「按列取候选」在控制器里由
  `editor.snapshot()` 现算（第 0 列的候选是 `firstNodes(载体)`，第 K 列是 `nextNodes(第 K 项)`），
  不向共享编辑器加方法，避免影响恶意服务器页。
- `src/ui/ServicePage.java` / `ServiceController.java`：零改动。
- 配置：`payload_export_dir` 键与 `Payload 生成配置` 分组零改动，没有新增配置项。

## 实施要点（供 tasks 与自检对齐）

- 链状态仍是 `List<String>`：第 0 项是载体，其后是 gadget。
- 列数 = 链长 + 1（最后一列是「当前末端还能接什么」；若为空则不再展开）。
- 列内项：`值`（节点 id）+ `显示名`（`nodeLabel` 的结果）。
- 点击第 K 列的值 `v`：`链 = 链[0..K-1] + v`，然后重算第 K+1 列。
- 「删除末节点」与「清空链」保持既有语义（载体不可移除）。
