# Design: 失败路径接入日志

## Root Cause

本轮要修的「Bug」是一条系统性的排查缺陷：**判断正确，但信息被丢弃**。

既有代码里 `catch (XxxException ignored)` 后面的注释几乎都写着同一个理由：
「不影响主流程」。这个判断是**对的**——单条代理连接失败确实不该拖垮整个代理，
一个节点的后续查询失败确实只是「没有后续」。问题出在处理方式：把异常丢掉，
等于把「失败过」这件事也一起丢了。

具体到三个场景，丢掉的代价完全不同：

| 场景 | 既有行为 | 丢掉信息的代价 |
| --- | --- | --- |
| 代理转发 | 连接静默关闭 | 使用者以为代理没生效，实际是上游连不上 |
| 引擎调用 | 输出流读取中断 | 超时与真正失败在报告里无法区分 |
| 载荷构建 | 步骤钩子静默失败 | 链看着生成了，但步骤明细缺一节，原因不明 |

因此修法不是「改判断」，而是「保留判断、补上记录」。

## 设计

### 只补失败路径

接入点统一取「原本就要丢弃异常」的位置。这样有两个好处：
一是不改变既有控制流，回归风险最低；二是记录点天然稀疏，日志量可控。

不动的部分同样重要：**成功路径不新增逐条记录**。代理每转发一条流量都写日志，
会把日志变成流量镜像，既无必要也拖慢转发。

### 记录级别的选择标准

| 级别 | 判定标准 | 本仓库实例 |
| --- | --- | --- |
| 错误 | 使用者期望的动作没有完成，且不是预期内的分支 | 引擎超时终止、载荷构建抛异常 |
| 警告 | 属于预期内的分支，但结果与「一切正常」不同，值得事后查看 | 节点没有后续、上游连接被拒绝 |
| 信息 | 生命周期事件，一行即可 | 代理启动 / 停止 |

刻意**不使用**「错误」记录「预期内的失败」：例如「某节点没有后继」是正常结论，
记成错误会让「翻错误日志」失去意义。

### 敏感内容边界

日志不写请求体、响应体、Shiro 密钥、CEYE Token。这些内容一旦落盘就长期存在，
而日志的定位是「排查工具本身的问题」，不是「留存测试数据」。
记录对象限于异常类型、异常消息、目标地址与端口这类定位信息。

### 超时与失败的区分

引擎超时与引擎执行失败在报告中本来就是两种结论，日志沿用同一口径：
超时记录为「超时已终止」并附上限秒数；失败记录为「执行失败」并附退出码或异常。

## 边界

- 不修改任何既有方法的签名、返回值与异常声明。
- 不修改既有配置项语义；新增配置项见 change `ui-logging-config`。
- 不改变依赖方向：新增的记录调用只依赖共享内核，不引入新的包间依赖。

## 本设计不改变哪些既有行为

- 全部功能的对外行为、界面提示文字与既有自检断言：不变。
- 构建依赖清单：不变。
- 既有七套 Java 自检：断言只增不减（本轮新增一套）。
