# Design: 漏洞分析界面

## Root Cause

界面层没有需要修的既有缺陷；本 change 要防的是**新引入**的两类退化：

**退化 1**：把三类动作合成一个按钮。
代价差异极大（本地分析 30 ms，调用链分析分钟级），合成一个按钮会让使用者在
只想看依赖坐标时被迫等分钟级任务。**设计对策**：按钮按代价分组，
标签上写明单位（如「调用链超时（秒）」并提示「大 jar 构建数据库是分钟级任务」）。

**退化 2**：在事件分发线程上跑分析。
本地分析虽快，但选中的依赖目录可能有上百个 jar；调用链分析更是分钟级。
放在事件分发线程会让界面假死，使用者会以为程序坏了。
**设计对策**：三类动作全部走后台线程，界面更新一律 `invokeLater` 回到事件分发线程；
用状态栏 + `busy` 标志表达「正在跑」，并在跑动期间禁用重复触发
（同一个工作目录里的数据库会被并发写覆盖）。

## 设计

### 为什么合在一页

三类动作的**输入是同一个 jar**，使用路径是「先秒级出结论 → 需要时再深挖 → 对可疑点定点看源码」。
拆成三个二级菜单会导致每换一步都要重新选一次文件。
因此一页两个二级项：`组件与漏洞`（本地分析 + 反编译 + 报告）与
`调用链查询`（引擎建库 + 数据库查询）。

### 视图与行为分离

沿用仓库既有三段式：`AnalyzePage` 只搭结构，`AnalyzeController` 持有行为。
页面不持有运行状态，控制器不直接持有页面对象（通过 `View` 接口回写）。

### 配置项进配置页

5 个可持久化参数全部落进「漏洞分析配置」分组，并按仓库约定
「控件声明 → 分组清单 → 读写映射三处相邻」，新增一项只改 `ConfigForm` 一处加
`ConfigController` 一行回填一行落盘。

### 跳转建议

报告里的建议是「页面 key」，界面把它渲染成按钮并通过既有的导航回调跳转。
按钮数量有上限（6 个），太多会把工具条挤成一片。

## 本设计不改变哪些既有行为

- 除 `NavController` 新增一行一级分类外，导航的既有分组顺序与交互完全不变。
- 配置页既有分组与读写映射不变，只新增一个分组。
- 既有七套 Java 自检断言只增不减。
