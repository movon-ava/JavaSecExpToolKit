# Design

## Context

上一轮 change `decouple-chain-engine` 已经把 Base64 编解码下沉到共享内核，
并建立了可机械执行的依赖边界自检（无环、声明分层、通用组件不依赖具体功能模块、共享内核单向被依赖）。
但通用链构建机制本身仍然住在具体功能模块里：`src/shiro/ChainsEngine.java` 既是对 java-chains 的封装，
又承载着 Shiro 场景的预置链模板与默认参数。

实测引用点（本设计的事实依据）：

| 被引用物 | 引用点 |
| --- | --- |
| `shiro.ChainsEngine` | `src/shiro/ShiroExploit.java`（100、101、103、107、110、111、132 行）、`src/Main.java`（923、932 行）、`tests/ShiroCheck.java`（169–192 行） |
| `util.Codec` | `src/shiro/ChainsEngine.java` 第 195 行、`src/shiro/ShiroEngine.java` 第 669、674 行 |

约束：Java 目标 release 8、Swing 界面、唯一第三方依赖 java-chains 2.0.0-beta4、
单个 change 原则上只覆盖一个执行角色的写入域、共享内核改动需主 agent 单独开 change。
动机见 proposal.md 的 Why。

## Root Cause

**通用机制与具体功能模块同包，是本次问题的唯一成因，不是缺少代码。**

1. 通用能力（载体枚举、节点导航、参数查询、载荷构建）与 Shiro 专属内容（6 条预置链模板、
   Shiro 密钥与命令的默认参数）写在同一个类里。任何其它功能要复用通用部分，
   只能引用这个位于具体功能模块中的类，于是产生 `payload → shiro` 反向依赖；
   上一轮建立的自检会把这种引用判为越界，复用路径被规则堵死。
2. 若改为在新包内重写一份 java-chains 封装，同一机制会存在两份实现：
   引擎升级时两份实现的载体数、节点导航与失败文案会分别漂移，
   且自检无法判断哪一份是事实源。因此**不能用重写代替复用**。
3. 因此解法只有一条：把通用机制搬到通用包，让具体功能模块反过来依赖它。

上一轮解耦已经把最后一处硬编码依赖（Base64）拿到共享内核，但**没有改变通用机制的归属**，
本次要解决的是归属问题，而不是继续搬零碎。

## Goals / Non-Goals

**Goals:**

- 通用链构建机制落在独立的通用包内，且该包只依赖共享内核。
- 既有 Shiro 路径零行为漂移：`shiro.ChainsEngine` 的公开 API、嵌套结果类型与 6 条预置链保持不变。
- 通用的载体分组表成为可机械校验的事实：分组并集必须等于运行时载体目录。
- 失败路径可观测：非法载体、空链、非法链、引擎未就绪都返回带原因的失败结论，不抛未捕获异常。
- 载荷只以「载体标识 + 节点序列 + 长度」进入可记录摘要，正文不落日志与文件。

**Non-Goals:**

- 不做界面层：页面、导航项、按钮与「填入抓包页 / Shiro 页」联动均不在本次范围。
- 不做配置持久化：配置键与配置页分组由后续 change 落地（见 proposal 的后续 change 表）。
- 不搬迁 `shiro.ChainsEngine` 的调用点：`src/Main.java` 属 UI 写入域，跨域改动推迟到 `payload-page`。
- 不新建投递、回连与靶场能力；不批量枚举参数组合。
- 不改共享内核，不引入任何新依赖。

## 设计的 API 边界（供实施与自检对齐）

- 通用包内三个源文件，职责单一，避免把逻辑堆进一个文件：
  - 引擎类：`init` / `isReady` / `statusMessage` / `nodeIds` / `payloadIds` / `paramsOf` / `nextNodes` /
    `build` / `normalizeParams`。
  - 结果类：成功标志、失败原因、Base64 文本、原始字节、字节长度、可记录摘要；
    提供成功与失败两个构造入口，失败入口保证其余字段为空。
  - 目录类：按用途的载体分组常量表，只暴露分组视图，不持有引擎实例。
- 门面类：`src/shiro/ChainsEngine.java` 保留原有公开方法（含 `templates` 与 `defaultParams`）
  与嵌套结果类型，方法体改为委派到通用包并把结果适配回原有类型。

## Decisions

1. **新增通用包承载机制，而不是把既有类整体搬到新包。**
   理由：整体搬迁会同时产生 `src/Main.java`（UI 写入域）与 `tests/ShiroCheck.java`（测试写入域）的编译改动，
   本 change 无法在单一执行角色的写入域内闭合。既有的「先解耦、后搬迁」做法与此一致
   （change `decouple-chain-engine` 的 Non-goals 明确写了「不移动文件位置」）。
   替代方案：整体搬迁 —— 推迟到 `payload-page`，届时界面直接改用通用包，门面再删。

2. **具体功能模块保留一个委派门面，公开 API 与结果类型不变。**
   理由：`src/Main.java` 与 `tests/ShiroCheck.java` 引用了嵌套结果类型，
   保留类型即可零改动保住既有调用方，把回归面收敛成「输出逐字符一致」这一条可判定的门禁。
   替代方案：直接改所有调用点指向新类 —— 跨写入域，且会让本 change 的自检在改名前无法运行。

3. **新包内的核心类不使用与既有类相同的简单类名。**
   理由：依赖边界自检用「简单类名 → 所属包」的索引解析限定名与 import；
   两个包出现同名类时索引会互相覆盖，扫描结果不再可信（会漏报或误报）。
   这条是硬约束，实施时新类必须另取名。

4. **结果模型同时承载两种形态。**
   理由：界面要复制文本、导出原始字节，若结果只留 Base64 文本，
   导出时需二次解码，且字节长度与文本长度的语义会被混为一谈。
   替代方案：只留文本 —— 已否决；只留字节 —— 复制到剪贴板还要重新编码，读屏与长度展示都变差。

5. **载体分组按用途维护，并以断言强制并集等于目录。**
   理由：分组是展示概念，一旦遗漏某个载体，界面上就再也看不到它，且不会报错——属于静默缺陷。
   替代方案：按字母序自动分组 —— 与 DESIGN-payload 的分组意图不符，且无法体现用途差异。

6. **失败以结果对象返回，不抛异常。**
   理由：与既有 Shiro 侧的失败结论风格一致，调用方拿到原因即可直接展示；
   抛异常会把「引擎拒绝的非法输入」与「程序缺陷」混为一谈，界面无法区分。
   替代方案：抛自定义异常 —— 既有调用方全部需要加 try，回归面扩大。

7. **依赖边界契约同步扩展，而不是把新包塞进既有包。**
   理由：`payload` 只依赖共享内核，属于新的通用层；若并入 `shiro` 包则复用目的落空。
   因此声明分层新增 `payload → util`，并允许 `ui → payload`、`shiro → payload`。
   同时把「通用组件不得依赖具体功能模块」的判定范围扩展到新包全部源文件，
   并增加一条反向用例，证明新增断言不是恒真。

## Risks / Trade-offs

| 风险 | 缓解 |
| --- | --- |
| 门面引入 `shiro → payload` 依赖边，可能被误读为「通用组件依赖具体功能模块」 | 依赖方向是具体功能模块指向通用包，符合声明分层；断言改为禁止 `payload` 反向引用 `shiro` / `probe` / `proxy` / `ui`，方向写进规格 |
| 委派后 Shiro 路径出现静默行为漂移 | 门禁是 `ShiroCheck` 标准输出与改动前逐字符一致，逐字符比对通过才算完成 |
| 引擎版本升级导致载体数或节点数变化，自检红灯 | 断言记录实测值并在失败时打印实际数量；数字变化即视为需要复核的信号，复核结论写入 `AI_REPORT.md` |
| 双形态往返断言过弱（只比长度）导致假通过 | 断言为「长度相同 + 首尾各 4 字节逐字节相同」，并对 Base64 文本做标准解码失败即失败的判定 |
| 结果摘要意外带上载荷正文 | 摘要只由载体标识、节点序列与长度拼成，并加「不含正文任意连续 16 个字符」的断言 |
| 新包被其它模块误用为具体功能依赖载体 | 边界自检的声明分层只放开 `util` 出边，`payload` 出现指向具体功能模块的引用即失败 |

## Migration Plan

1. 先在通用包内落地三个新文件（目录、结果、引擎），此时既有代码零改动，可独立编译。
2. 再把 `src/shiro/ChainsEngine.java` 改为委派门面，保留公开签名与嵌套结果类型。
3. 同步依赖边界自检的允许边与通用组件范围，补反向用例。
4. 新增引擎自检，跑通全部断言。
5. 回归：五套既有 Java 自检 + Python 单测全绿，`ShiroCheck` 输出逐字符一致。
6. 由主 agent 收尾：备份、报告与进度、构建并校验产物时间。

**回滚策略**：本 change 只涉及源码与自检，无数据、无配置、无外部状态变更；
回滚即 revert 本次提交，`shiro.ChainsEngine` 与其调用方会随之一并回到委派前的实现。

## 与既有模块的边界（本设计明确不改变的行为）

- 界面：不新增导航项、页面与按钮，`src/ui/**` 与 `src/Main.java` 的内容与行为不变。
- 配置：不改配置键、不改配置页分组，既有配置文件完全兼容。
- 探测与代理：不触碰 `python/fj_probe.py`、探测与抓包相关代码与其行为。
- Shiro：密钥校验、发包、命令回显与 6 条预置链的语义不变，公开签名不变。
- 依赖边界：无环、叶子层无出边、共享内核单向被依赖三条约束维持原样，本次只扩展声明分层与判定范围。

## 共享内核影响

本设计**不修改**共享内核（`src/util/**`、`src/config/**`），只读取其中既有能力：

- `util.Codec.base64(byte[])` 的调用方：`src/shiro/ChainsEngine.java` 第 195 行、
  `src/shiro/ShiroEngine.java` 第 674 行；`util.Codec.decodeBase64(String)` 的调用方：
  `src/shiro/ShiroEngine.java` 第 669 行。本设计不改变这些调用点。
- `src/config/AppConfig.java` 本设计不触碰，四个 payload 相关键由后续 change `payload-config-keys` 落地。
