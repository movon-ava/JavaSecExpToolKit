# Design: 漏洞分析 - 本地依赖分析与调用链查询

## Root Cause

本轮实现过程中定位到三个真实缺陷，共同点是**都不会报错，只会让结论静默失真**：

**缺陷 1**：`pom.properties` 的键大小写不匹配，让整个本地分析静默退化。
读取时为了兼容大小写不一致的打包工具，把键统一转成小写存入 Map；取值却用了驼峰常量
`groupId` / `artifactId`，于是**永远取不到值**。每个 jar 的 `META-INF/maven/**/pom.properties`
都读不出坐标，整份清单退化到「按文件名推断」，版本判定随之全部失真，
而界面上看不出异常（结论照出，只是依据错了）。
修法：改用小写常量并在常量上写明原因。

**缺陷 2**：版本比较的缺段语义让预发布版倒挂。
原本把缺失段按数字 0 补齐，于是 `1.0-rc1` 被判成**大于** `1.0`（`rc1` 与补出来的 `0` 相比）。
修法：引入 `MISSING` 哨兵对象——缺段对数字段按 0 看待，对字符串段（`rc1` / `beta2`）
视为「正式发布」，即比任何预发布标记都大；同时修正比较方向（`sign` 曾写反，由自检抓出）。

**缺陷 3**：groupId 缺失时的匹配取舍。
只按 artifactId 匹配会把 fork 或同名包误判成受影响的组件；直接拒绝匹配又会让
「只有文件名来源」的依赖永远判不出结论。
修法：groupId 存在时必须核对前缀；缺失时放行但把结论可信度降到「低」，
由 `Finding.Confidence` 明确告知使用者这条判定建立在推断之上。

## 设计

### 分层与代价

| 层 | 数据来源 | 代价 | 触发方式 |
| --- | --- | --- | --- |
| 本地依赖分析 | jar 内的 Maven 坐标 | 秒级 | 永远先跑 |
| 调用链分析 | 全量字节码的调用图 | 分钟级 | 使用者显式触发 |
| 反编译 | 字节码 | 秒级（整包） | 使用者显式触发 |

### 依赖坐标的来源分层

| 优先级 | 来源 | 理由 |
| --- | --- | --- |
| 1 | `META-INF/maven/**/pom.properties` | 打包时由 Maven 写入的事实 |
| 2 | `META-INF/maven/**/pom.xml` | 同为打包产物，但可能被 shade 改写 |
| 3 | `META-INF/MANIFEST.MF` | 由打包插件写入，粒度粗 |
| 4 | 文件名推断 | 只是推测；同一组件有多种命名 |

读取全部走 `JarFile` 的条目枚举：**不解压、不落盘、不加载任何类**。
目标 jar 可能来自任意来源，解析期间不得让它获得执行机会。

工程 `pom.xml` 走 DOM 解析并**关掉 XXE**，只取顶层 `<dependencies>`，
跳过 `dependencyManagement` 与 `profiles`——后者是「声明但未生效」的依赖，
混进来会产生大量假阳性。

### 规则表

规则由本项目自己编写：上游 `jar-analyzer` 的规则文件是 GPLv3，
搬进本仓库有许可问题。内容取自各组件公开公告，且只收录「判定后能接上本工具后续动作」的组件。

版本区间只支持三种形态：`BELOW`（`< upper`）、`AT_MOST`（`<= upper`）、
`RANGE`（`lower <= v <= upper`），足以表达已知公告。
无法比较的版本一律不匹配（宁可不报，不可误报）。

### 外部引擎的三处实测约束

| 约束 | 处理 |
| --- | --- |
| 固定把 `jar-analyzer.db` 写到**工作目录**，无输出路径参数 | 显式接收工作目录，产物路径由本工具算出，不猜 |
| 构建大型 jar 是**分钟级** | 超时上限进配置页（默认 300 秒），超时 `destroyForcibly` 杀**进程树** |
| 构建期产生 `jar-analyzer-temp` | 分析完成后清理，不留给使用者收拾 |

超时低于 30 秒时提前拦下并说明原因，而不是让使用者等一个注定失败的任务。

### 查询为什么走 Python

SQLite 是文件格式而非 JDK 能力，要读它就得引 JDBC 驱动，与「禁止新增依赖」冲突。
Python 标准库自带 `sqlite3`，且本项目探测引擎本来就是「Java 收集参数 → Python 执行」，
这条既有通道正好承接查询。连接一律 `mode=ro`（只读），绝不写库。

Java 侧只把「哪张表、要什么」翻译成命令行，**不在 Java 侧复制一份 SQL**。

sink 清单同样自写（26 项）：上游的 sink 与 SCA 数据都在 GPLv3 的 GUI 侧，不在 engine 里。

### 反编译

实测运行期依赖 `lib/java-chains-cli-2.0.0-beta4.jar` 已含 CFR（`org/benf/cfr`），
因此直接调用等于零新增依赖、零额外进程（实测整包 84 个类 3.5 秒）。
外部反编译器 `jar-analyzer/jsd` 只在「本机没有 JVM」这类场景有优势，
因此只保留命令行拼装能力作为备选，不作为默认路径。

指定类名反编译时把 jar 加进 CFR 的 `extraclasspath`，否则被反编译的类引用同包其它类时
解析不到父类 / 接口，只能输出残缺源码（CFR 的 `Builder` 没有 `withClassPath`）。
CFR 是同步 API、无法中途打断，因此超时在这里是「完成后判定」而不是「中断」，
这是已知局限。

## 边界

| 包 | 定位 | 出边 |
| --- | --- | --- |
| `src/analyzer/` | 分析内核：读文件 / 跑规则 / 调外部程序 | **无**（叶子层） |
| `src/analyze/` | 编排层 | 只依赖 `analyzer` |

`analyzer` 作为叶子层的好处是自检可以直接驱动它，也能被界面之外的入口复用。

## 本设计不改变哪些既有行为

- Fastjson 探测、代理抓包、抓包转换、Shiro 利用、Payload 生成、预设链、toString 链、
  带外 Jar、恶意服务器、文件上传：完全不变。
- `src/config/**`、`src/util/**`：只读。
- `src/pom.xml`：只在 `<resources>` 的 python includes 里加一行，**未新增依赖**。
- 既有七套 Java 自检与 Python 单测：断言只增不减。
