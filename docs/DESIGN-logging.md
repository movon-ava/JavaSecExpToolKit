# Design: 日志记录（按日期分文件 + 定期清理）

## Root Cause

排错困难的成因不是「没写日志」这么笼统，而是三个具体缺口。三者的共同点是
**都不会报错**，只会让现场消失。
**缺口 1：异常被静默吞掉。** 源码里 107 处 catch 中有大量以「忽略」结尾，注释几乎都写着
同一个理由：「不影响主流程」。这个判断本身是对的——单条代理连接失败确实不该拖垮整个代理，
某个节点没有后继也确实是正常结论。问题出在处理方式：把异常丢掉，等于把「失败过」这件事
一起丢掉了。于是使用者的体验是「点了按钮没反应」，而不是「报错」。

**缺口 2：后台线程的异常无处可去。** 代理的接受循环、隧道泵、引擎与脚本的输出读取都不在
事件分发线程上。这些线程抛出的异常默认只打到标准错误；从图形界面启动时标准错误没有接收方，
等于凭空消失。使用者报告现象时，现场早已不存在。

**缺口 3：没有时间基准。** 即使事后从别处拿到一些线索，也无法回答「这个问题是今天出现的，
还是一周前就有」——没有任何按时间落盘的东西可查。

具体到一个已发生的例子：代理转发到上游失败时，转发逻辑把异常包成 IOException 抛给上层，
上层又把它吞掉并关闭连接。使用者看到的是「浏览器访问超时」，而真实原因（上游连不上、
目标端口写错）被丢弃了两次。

因此修法是**保留既有判断、补上记录**，而不是改行为。

## 设计

### 为什么内核放在共享内核层

日志必须能被**任意**模块调用。本仓库的依赖方向被约束为单向（见依赖边界规格），
功能模块之间不允许互相依赖，因此日志只能沉到被所有层依赖的共享内核里。

这一层的代价是**不许有任何出边**：内核不能反过来引用界面或任何功能包，只能依赖 JDK 标准库。
级别过滤、目录解析、清理规则，全部自包含。

### 两个类，一条职责分界

| 类 | 职责 | 判定方式 |
| --- | --- | --- |
| LogFiles | 名字怎么拼、哪个名字代表哪一天、哪些该删 | 纯计算，可脱离文件系统断言 |
| Log | 级别过滤、时间戳、异常栈、落盘、跨天切换 | 真实写文件 |

拆开的理由是「保留天数是否算对」属于最容易写错、又最不该靠造文件去猜的一类逻辑。
分界一旦划清，规则层可以被逐条断言（含跨月、跨年、闰年），而写入层只需验证
「真的写进了当天文件、跨天真的换文件」。

### 关键取舍

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 写入失败怎么办 | 静默丢弃这一条 | 日志是旁路。让它影响主流程，比没有日志更糟 |
| 并发写入 | 单一锁内串行写 | 日志量远低于吞吐瓶颈；无锁队列会引入丢行与顺序错乱 |
| 保留语义 | 最近 N 天，含今天 | 与使用者直觉一致；写成「N 天前开始保留」会多留一天 |
| 保留天数越界 | 归一到 1 | 填 0 或负数多半是手滑；按字面执行会把正在写的文件一并删掉 |
| 清理频率 | 启动一次 + 跨天一次 | 每次都扫目录是浪费；只在启动清理又会漏掉长期运行的会话 |
| 日期来源 | 可替换 | 跨天切换无法靠等待验证，必须能把日期注入进来 |
| 是否默认开启 | 开启 | 排错能力不该需要使用者先手动打开 |

### 清理的安全边界

「定期清理」的破坏性来自「删错东西」，因此设三道闸：

1. 只有严格匹配 app-日期.log 形式的文件名才进入候选（月份必须补零、日期必须真实存在），
   目录里其它文件一律不碰；
2. 候选必须是常规文件，且其父目录恰好是日志目录自身（越界即跳过）；
3. 单个文件删除失败（被占用）只跳过，不中断清理、不影响写入。

日志目录默认落在用户目录下、与配置文件同级，避免写进安装目录（可能只读）。

### 两次初始化

启动顺序上有一个硬约束：日志必须在**最需要它的那一段之前**就绪。当前启动流程是
「建控件 → 读配置 → 建控制器 → 预热（约 1 至 2 秒，java-chains 元数据最重）→ 显示窗口」。
如果日志初始化跟在读配置之后，那么读配置本身、控件构建与整个预热都处于无日志状态——
而这几步恰恰最容易在别人机器上出问题。

因此分成两次：

| 时机 | 目的 | 取值来源 |
| --- | --- | --- |
| 进程启动、读配置之前 | 保证最早的失败也有记录 | 内建默认值 |
| 读取配置之后 | 让使用者的设置生效 | 配置页保存值 |

初始化动作幂等且可重复调用：第二次调用按新设置重开当天文件（追加，不覆盖）。

### 接入点的级别取舍

| 级别 | 判定标准 | 本仓库实例 |
| --- | --- | --- |
| 错误 | 使用者期望的动作没有完成，且不是预期内的分支 | 引擎无法启动、载荷构建抛异常、初始化失败 |
| 警告 | 属于预期内的分支，但结果与「一切正常」不同 | 上游连接被拒、跳过损坏的 jar、超时终止 |
| 调试 | 正常收尾路径，只在需要细究时看 | 隧道两端断开、流已关闭、无后继节点 |

刻意**不用**「错误」记录预期内的失败：例如「某节点没有后继」是正常结论，
记成错误会让「翻错误日志」失去意义。

### 敏感内容边界

日志不写请求体、响应体、Shiro 密钥、CEYE Token。这些内容一旦落盘就长期存在，
而日志的定位是「排查工具本身的问题」，不是「留存测试数据」。记录对象限于异常类型、
异常消息、目标地址与端口这类定位信息。

### 依赖边界的放宽

接入时发现一处结构性阻碍：proxy 与 analyzer 此前被声明为**零出边**的叶子包，
因此无法调用共享内核里的日志通道——而它们正是静默失败最密集的两处（分别 12 处与 9 处）。

改法是引入「功能层叶子」这一档：只承载机制、不做复用设计的包允许依赖共享内核，
仍**不允许**依赖任何功能层。这条放宽不会引入环（内核自身零出边），也不会让这些包获得
反向感知能力。判定上由两条断言分别咬住：内核叶子（零出边）与功能层叶子（只允许指向内核）。

## 边界

| 包 | 定位 | 出边 |
| --- | --- | --- |
| src/util/ | 共享内核（含日志） | 无 |
| src/proxy/、src/analyzer/ | 功能层叶子 | 只允许 util |

## 本设计不改变哪些既有行为

- 全部功能模块的对外行为、返回值、界面提示文字与既有配置项语义：不变。
- 既有失败路径的处置方式：不变，只增加记录。
- 构建依赖清单：不变（未新增依赖）。
- 既有八套 Java 自检与 Python 单测：断言只增不减。
